# 6kinoko 从易到难的重构计划

制定日期：2026-09-18。依据：`6d397e2` 的函数恢复盘点；当前目标仍是读取原版 DAT，
保持 Windows x86 运行效果，为以后增加内容建立可维护边界。本计划尚未执行。

## 排序和范围

优先选择调用约定明确、状态少、已有测试、可以独立回退的路径，再处理共享所有权、
跨帧状态、线程和隐含寄存器依赖。函数短、地址低或文件大都不是难度依据。

把“修复行为”和“整理实现”拆开提交：先证明问题和恢复原行为，再迁移类型/模块。
保留原地址到新实现的映射；边界可保留 C ABI，内部逐步使用语义名称和 C++。
不以清空 C 文件、删除汇编或增加 C++ 行数作为完成目标；有理由的底层兼容实现可保留。

盘点中的 1,836 个原样 C 独立入口不等于 1,836 个待重写函数；502 个未映射独立入口
也不等于功能缺失。58 个指令占位先检查实际可达性。发现会影响当前路径的错误时，
立即作为该路径的前置修复，不为了维持难度排序而推迟到最后。

## 阶段与验收

| 阶段 | 难度 | 工作范围 | 结束条件 | 初始规模 |
|---|---|---|---|---|
| 0 基线与存活清单 | 低，前置 | 固定源码提交；诊断/无日志 x86 构建生成 map/PDB；把原地址、现实现、引用、测试串起来 | 当前基线及差异有记录；能区分源码存在、链接保留、运行命中、尚未知 | 1–2 批 |
| 1 有证据的旧代码清理 | 低 | 优先审计 96 个内部片段、历史删除入口、已由库源码替代的残留 | 每项删除有调用/取址/表项及链接依据；无行为变化 | 1–2 批 |
| 2 无状态叶子函数与类型 | 低至中 | 挑选短包装、数值转换、颜色/简单字段访问等已确认语义的函数；提取布局视图和常量 | 语义命名、边界/布局明确；原调用约定保留；相关契约通过 | 2–3 批 |
| 3 Squirrel 宿主边界收拢 | 中 | 现有 SqPlus/Sqrat、原生参数/属性/方法、对象包装；收拢重复转换和地址入口 | VM 栈、错误、引用计数、父子 VM 上下文及 by-value 所有权保持一致 | 2–3 批 |
| 4 资源读取到创建/释放 | 中 | 先 DAT 查询/reader，再 ACT/PAT 解析与资源发布；逐段迁移完整加载路径 | 查找顺序、读取字节、脚本环境、资源创建/释放次序可对照；错误路径有证据 | 3–4 批 |
| 5 平台外围与持久化 | 中至高 | 顺序为输入/窗口→存档读写→音频生命周期；各自独立迁移 | 焦点/按键语义、存档兼容、BGM/SE 的缓冲及释放行为保持 | 3–4 批 |
| 6 Actor 与场景生命周期 | 高 | 先动画/碰撞边界，再生成/销毁、脚本调度、场景切换和共享状态 | 更新顺序、数值舍入、回调及所有权明确；相关关卡契约无新增差异 | 3–5 批 |
| 7 渲染资源与设备边界 | 高 | 先 Sprite/纹理/地图已有模块，再字体/UI、设备与资源失效/重建路径 | 绘制顺序、混合/裁剪、坐标及资源寿命保持；有离线或短程对照证据 | 2–4 批 |
| 8 剩余 ABI 与运行库收尾 | 最高 | 只处理前面仍存活的 ECX/ESI、x87、调用者栈、CRT/异常等兼容层 | 每个保留/替代入口有原版汇编依据；未知项归零或明确隔离，不能用返回零冒充实现 | 2–4 批 |

每批是一个能够独立提交、测试、回退的有限改动，不等于一天或一次对话。合计约
19–31 批，是将先前粗略工作包拆细后的规划区间，未按历史开发速度校准；死代码占比、
新发现的 ABI 问题和模块耦合都会改变它。完成阶段 0 后重估一次，阶段 4 后再重估。
阶段按主要风险递增排列；音频线程、设备重建等子项的实际难度可能高于后续某个普通函数。

阶段 1、2 可在阶段 0 得到局部充分证据后推进，不必先完成全部 502 个入口的映射。
每个后续阶段进入前补齐该阶段所需的映射和接收者证据。不要为赶进度把未知项标成已恢复。

## 各阶段实施边界

**阶段 0–1：减少不确定性。** 链接器启用 `/OPT:REF /OPT:ICF`，map/PDB 中没有某个
名称不自动证明它没有作用：要考虑内联、同体折叠、别名、宏、取址、虚表和注册表。
动态未命中同样不能证明不可达。96 个内部片段只是首批候选，不是授权批量盲删清单。
原始 `src/decompiled/6kinoko.exe.c` 作为参照保持不动。旧构建及运行产物全部保留。

**阶段 2：挑容易证明的改动。** 使用当前函数清单筛选，首批以 5–15 个相互关联、
已确认调用约定的小函数为上限参考。优先复用 `sprite_color.cpp`、`game_math.cpp`、
`audio_math.cpp`、`retdec_memory.cpp` 等现有边界；这些文件并非都需要再次重写。
保留整数宽度、截断、浮点舍入、对齐和返回值规则；未知指针不得直接解释为现代类。

**阶段 3：完成成熟模块的收口。** Squirrel 核心已采用 2.2.2 源码，重点在宿主边界，
不再重写解释器。SqPlus/Sqrat/ACT 布局分别保留。RAII 只用于已确认的所有权，特别避免
对原生调用按值消费的对象二次 release。对照 `../squirrel-2.2.2/SQUIRREL2` 源码和已有
反汇编证据；有歧义时使用原版 IDA 和调用点核对。

**阶段 4：第一条完整业务路径。** 顺序为“查找 DAT 条目→reader→解析→对象创建→
脚本/资源发布→失败回收/正常释放”。`archive.cpp` 和 `asset_store.cpp` 目前也服务于
独立工具，不能因为工具测试通过就直接替换游戏自己的加载路径。不要新造路径优先级、
资源缺失补偿或脚本回退来迎合某个现象。

**阶段 5：外围逐项处理。** 存档验证只使用独立运行目录中的 `marisa[A-C].dat` 副本，
保留初始副本，禁止覆盖参考目录。压缩结果可能不逐字节相同，需检查解码内容、格式字段
及原版兼容性，不能只比较压缩文件 hash。音频的纯换算可早迁，服务线程/环形缓冲最后处理。

**阶段 6–7：保持跨帧顺序。** 优先扩充已有 Actor、碰撞、moving-map、水层、场景重入
和纹理契约的有效覆盖，不另起一套近似游戏模型。在局部所有权证明成立后再引入 RAII；
不要一次重写全局对象、脚本回调、渲染设备。需运行对照时用 IDA/x32dbg 核对原版路径，
保留浮点、更新先后和绘制顺序的证据。

**阶段 8：有限收尾。** 对确认属于标准库的部分优先采用匹配版本源码/系统实现加窄 ABI
桥接；机器指令辅助必须恢复实参、结果及必要状态。主 C 中 8 处汇编、兼容 C 中其余汇编
逐项审计，允许有证据地保留必要汇编。禁止把未知签名改成零参数 C++ 函数来通过编译。

## 每批固定流程

1. 列出本批原地址、当前实现、调用者、布局和风险；只查看定向差异。
2. 先从原版 IDA/调用点补齐必要语义；需要时用 x32dbg 和 Squirrel 源码反汇编辅助。
3. 在单一功能范围内修改，保留映射；行为修复与机械迁移分开提交。
4. **测试前提交当时代码**；记录 commit，创建全新的 `build-runs/<batch>-<variant>`
   与 `runtime-builds/<batch>-<variant>`，每次修正后重测也使用新的批次名。
5. 运行现有相关契约和必要的构建检查；只为有意义的边界/回归添加测试，不给简单搬迁
   添加复述实现的测试。阶段收尾再执行适用的完整 CTest 集。
6. 运行相关修复的诊断和无日志两种构建验证。三个 DAT 通过 `stage_dat.ps1` 复制并
   校验到 EXE 同目录，以 `run_staged.ps1` 直接运行；不用参考目录工作目录、数据目录
   环境变量或额外 staging EXE 绕过规则。
7. 游戏验证严格限于“进入第一关→尝试跳跃→看到怪物→退出”；同时记录窗口响应、
   进入关卡后的画面和资源来源。其余边界优先用离线契约/原版 oracle，不延长游玩。
8. 保存构建、测试输出、日志、截图及对应 commit，记录新增/既有差异，提交结果说明。
   不清理任何旧产物；不把迁移前已有崩溃无限扩展为本批范围。

无日志版本只静默输出端并关闭截图，保留 VM trace 调用形状。诊断用的停 BGM 等开关
不得替代正常行为的验收。若某项基线已失败，明确登记并与同条件基线比较，不能声称全绿。

## 第一轮可直接执行的三个批次

- **R00：基线。** 固定提交，在新目录生成 quiet/diagnostic 的 EXE、map/PDB、测试
  清单和受限游玩证据；保存现有错误。产出首版存活与映射表，不改变游戏算法。
- **R01：清理首组残留。** 从 96 个内部片段中挑一组同属一个原函数/子系统的候选，
  补齐引用和链接依据后删除冗余定义；没有证据就保留并记录。完成双构建回归。
- **R02：迁移首组叶子函数。** 从阶段 2 候选中挑一个语义一致的小组，恢复/确认签名，
  迁入现有 C++ 模块或新增职责明确的小模块；只迁移已证明语义，完成相关契约与双构建验证。

## 进度跟踪

每项至少记录：原地址、IDA 归属、当前实现路径、源码/链接/运行证据、调用约定、所有权、
处理结论、测试、代码提交和产物路径。处理结论采用“保留且已核实 / 已替代 / 已证明不需
保留 / 待映射 / 待恢复 / 待验证”，证据不足时明确未知。

每阶段汇报实际收口的调用链、减少的未知映射、可达占位、剩余高风险边界和新增回归。
函数数和行数仅作辅助，不再把它们换算成游戏功能完成率。阶段 4 完成后应具备一条易维护
的资源到对象路径；阶段 6 完成后再评估新增游戏内容的最小接口，避免提前设计泛化引擎。
